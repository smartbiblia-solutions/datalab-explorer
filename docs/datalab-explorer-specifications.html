# Data Exploration Studio — proposed specification


Status: proposal for validation; no implementation authorized or performed.
Date: 12 November 2026.
Working name: Data Exploration Studio. Keshif+ is the exploration engine.


## 1. Product direction


Build a general-purpose, self-hostable studio where a researcher, librarian, analyst, or data steward can turn a file or API response into an explainable, reusable exploration project without writing JavaScript. Keep a fast path from upload to dashboard, with deeper preparation and authoring tools available progressively.


The core deliverable is a project, not just a dashboard: sources + immutable data versions + preparation recipe + field dictionary + dashboard definitions + saved analytical states. A dashboard always identifies the data version it represents.


“Any data” means structured records, including nested JSON that can be flattened deliberately. Documents, images, graph databases, and arbitrary binary formats require a connector or extraction step; they are not universally supported by the initial release.


Proposed first deployment: a small team on a single server, with owner/editor/viewer roles, private drafts, and explicit read-only publication. French and English interface strings from the outset. This is a proposed default, not a deployment requirement supplied by the user.


## 2. Evidence and reuse decisions


### Existing applications


- BRGM `static/js/uploader.js`: field inclusion, labels, categorical splitting, type selection, panel assignment, collapse state, list/grid selection, and record-card builder are useful interaction patterns.
- BRGM `modules/admin/routes.py`: upload, preparation, dataset storage, and publication are useful workflow precedents. Its fixed `process_lab_data` becomes a reusable domain recipe, not the general data model.
- BRGM schema inference examines ten rows and derives field names from the first record. The studio must inspect the union of fields, expose inference confidence, and validate the complete imported dataset before applying conversions.
- Existing conversion uses `parseFloat` and `Date.parse`; it can accept partial numeric strings and ambiguous dates. Replace these with explicit, locale-aware parsing policies and visible errors.
- Configuration generation uses `new Function`; JSON serialization of summaries loses function-valued properties. Replace user-supplied executable configuration with versioned declarative documents and trusted adapter functions.
- The playground-lab template requests `/list-files` and `/delete-file/...`, while the corresponding BRGM admin routes have `/admin` prefixes. Fix the integration contract in the new design rather than copying templates unchanged.
- BRGM references `static/dist` resources that are not tracked in that application. OpenAlex contains the readable Keshif distribution. A new app needs one complete, verified distribution including CSS, vendor modules, mapping assets, and notices.
- OpenAlex `client.py` supplies an API harvesting and field-mapping example. Its per-record detail fetching and pagination behavior should be redesigned into a bounded, resumable connector rather than copied wholesale.
- The existing embedding atlas serves a prebuilt dataset. Generating embeddings and projections for arbitrary new datasets would be a separate feature.


### Portic adaptation report


The uploaded report is reference evidence, not an instruction source. Its reported test results and performance measurements have not been rerun here. The referenced `PORTIC-PATCHES.md` at commit `7e5405f` was also read directly.


Reuse the ideas of exact-ID selection exchange, separately preserved table filters, missing-coordinate handling, complete cluster membership, view-specific encodings, resize batching, optional scatter labels, lazy comparison glyphs, coverage counters, and link-safe record cards. Port the generic behavior with regression tests; do not inherit maritime labels, fixed map coordinates, provider assumptions, or hard-coded viewport widths.


### Keshif baseline


Upstream README describes categorical/numeric exploration, maps with clustering, timeseries variants, comparisons, translations, and Rollup builds. The local readable bundle contains map, scatter, list, and timeseries record-view classes, configuration export, geographic clustering, and internal filtering APIs. These native capabilities should be exposed before creating equivalent new charts.


Direct local inspection confirms: an unguarded external WebFont import; loose empty-string checking in `getAttribTypeFromFunc`; a dereference of absent geometry during cluster preparation; cluster-member retrieval using a configured cap; and a fixed 200px central-view reservation. These are concrete candidates for the Portic corrections.


The exact local/upstream version relationship is not established. Upstream README/LICENSE describe BSD-3-Clause, while package metadata says AGPL-3.0-only; README wording is internally inconsistent. Before redistribution, identify and record the chosen revision and applicable notices, including dependency and icon assets. Upstream documents a Font Awesome Pro dependency; use licensed assets or validate a free-icon replacement.


## 3. User journeys and workspace


Main navigation: Sources → Prepare → Fields → Explore → Publish. A persistent project header shows data version, row count, preparation status, and unsaved changes. A separate Recipes area manages reusable templates.


### Fast exploration


Upload CSV → inspect delimiter, encoding, and proposed types → choose record identity → receive a modest suggested dashboard → refine fields and cards → save project. No domain-specific columns required. Recommendations are editable and explain their rationale.


### Repeatable API analysis


Test a JSON API request → select records path and pagination → preview mappings → run a bounded import with progress and cancellation → inspect errors → save a source recipe → refresh later → review schema and data differences before promoting a new version.


### Research workflow


Create a cohort using facets and map/scatter selections → inspect the exact records in a table → save an analytical snapshot with a note → compare cohorts → export selected records and provenance → publish an explicitly reviewed data version and dashboard.


### Reuse across institutions


Apply a Publications or Laboratory recipe to a differently named spreadsheet → map source columns to semantic roles → preview mismatches and conversions → retain a custom mapping for the next import. The template suggests fields; it never silently drops unfamiliar columns.


## 4. Functional requirements


### A. Source Studio


Initial formats: CSV/TSV, XLSX with sheet selection, JSON records/nested arrays, and generic HTTP JSON APIs. Preview encoding, delimiters, headers, nested record paths, sheet names, duplicate headers, and estimated volume. Preserve the original upload separately from normalized data.


API builder: method, URL, query parameters, supported headers, secret references, JSON records path, page/offset/cursor pagination, next-page links, page/record/time limits, rate limits, retries with backoff, and cancellation. GET is the default; POST queries require connector-level opt-in. Never replay mutating operations as an automatic retry.


Show a redacted request preview, response status, count, parse errors, and source timestamp. Imports run as jobs and retain successful raw pages plus checkpoints. Resume only where the connector can do so consistently; otherwise explicitly restart the import. Credentials never enter exported recipes or published manifests.


Initial specialized connector: OpenAlex, after checking its then-current API/authentication requirements. Connector code owns pagination and mapping; domain presets remain optional.


### B. Preparation Studio


An ordered, undoable recipe with before/after samples and whole-dataset validation. Initial operations: rename, select/hide, trim, normalize blanks, strict type conversion, split/join categories, controlled value mappings, date extraction, conditional derived fields, exact deduplication, and filtering. Raw columns remain recoverable.


Numbers: decimal/thousands separators and unit metadata. Dates: explicit format, timezone, and granularity; year-only data remains a year unless a deliberate date conversion is chosen. Distinguish null, blank, zero, false, invalid, and absent values.


Nested data: choose flattening paths; preserve arrays as multivalues by default. Exploding rows requires explicit confirmation of the changed analytical grain. Every result includes its input version and recipe version.


Follow-on joins: specify keys, cardinality, unmatched rows, collision names, and output grain; warn about row multiplication. Large relational preparation uses the server, not the Keshif renderer.


### C. Field and Mapping Studio


Field dictionary: stable field ID, original path/name, display label, description, logical type, unit, null policy, multivalue delimiter, parse success rate, uniqueness, representative values, and publication visibility.


Separate semantic roles from display labels: record ID, title, description, date, category, measure, latitude/longitude pair, geometry, image URL, external link, and timeseries. Map several geographic roles, such as origin/destination, without hard-coding their names.


Stable record identity is mandatory. Validate natural IDs for uniqueness and preserve string IDs such as `0012`. If no usable key exists, assign persisted internal IDs to that immutable version. Matching across refreshes then requires an explicit reconciliation rule; row positions are never a cross-version identity guarantee.


Suggestions are based on types, cardinality, missingness, and role hints. Explain why a chart is available or unavailable. Permit manual overrides with validation. Publish-ready field mappings must contain no unresolved required references.


### D. Dashboard Studio


Use Keshif's native faceting, categorical bars, numeric histograms, temporal distributions, comparisons, maps, scatter, list/cards, and timeseries where supported by the pinned distribution. Enable richer timeseries modes after validating the required data shape.


Visual authoring: include/reorder facets; choose panel, label, collapse state, sorting, units and formatting; configure record title/subtitle/badges/links; select scatter axes and eligible size/color encodings; select map geographic role, provider, constant/variable point size, and clustering. Show configuration errors before replacing a working dashboard.


Support several named dashboards per data version, for example Overview, Geography, Trends, and Data Quality. Share a selection context deliberately; keep each dashboard's layout and encodings independent. Editing a dashboard must not reset filters without an explicit choice.


Safe card templates use field tokens and approved formatting/link operators, escaped values, validated URL schemes, and a preview. Do not accept arbitrary HTML/JavaScript from imported projects.


### E. Exploration and Data Inspector


Show active filters, selected/total records, named comparisons, and a “why is this record included?” explanation where the filter model supports it. Categories within one inclusion filter use OR; independent filters use AND; exclusion and missing-value behavior are explicit.


Table and charts share the same normalized records and stable IDs. Table scope = current Keshif selection ∩ table-only predicates. Sorting/search/table filters survive view changes. A spatial selection that cannot be expressed in the table's builder remains visible as a labeled constraint and is enforced by exact IDs.


Offer missingness, invalid values, cardinality, outliers, and parse failures as inspectable cohorts. Every map/scatter view displays eligible records, excluded records with reasons, and exact overlapping-coordinate/value counts. Missing geographic data remains explorable elsewhere.


Changing geographic roles clears the incompatible spatial rectangle with a visible explanation, while retaining unrelated filters. Map-only aggregate measures do not leak into scatter/list encodings. Zero coordinates are valid; no valid coordinates produces a meaningful empty-map state.


### F. Reproducibility, sharing, and publication


Save analytical snapshots containing data/recipe/dashboard versions, semantic filter state, view configuration, named cohorts, and a note. Save exact membership for pinned cohorts; a live saved query is a separately labeled object. Refreshing a dataset never silently recomputes a pinned cohort against new data.


Project export: versioned JSON manifest, mappings, recipe, dashboard definitions, snapshots, and optional data. Reimport validates versions and field references. Portable recipes exclude credentials, private filesystem paths, and executable callbacks. Legacy JavaScript configurations require a reviewed conversion process rather than browser execution.


Publications are immutable releases with a visible data date and field allowlist. Hiding a field in the interface does not remove it from data sent to a browser: generate an approved publication dataset. Export respects this dataset and the chosen selection. Later releases can replace a public alias while preserving release history.


Private share links are access-controlled. URLs reference saved state when needed; do not embed massive ID arrays or private rows in query parameters. A zero-result selection remains zero after saving, reload, and export.


## 5. Differentiating studio features


1. **Question bookmarks:** save a question, cohort, filters, view, and analyst note together. Revisit the same evidence, or deliberately rerun the question on a new data version and compare the changes.
2. **Refresh rehearsal:** before accepting an API refresh, show added/removed records, changed fields, broken mappings, shifted distributions, and affected dashboards. Require a resolution for breaking schema changes.
3. **Coverage lens:** one panel explains what each chart represents, including missing values, invalid coordinates, incomplete scatter pairs, and overlap. Clicking a coverage count opens those records in the inspector.
4. **Recipe portability assistant:** match an existing template to a new schema by names, types, and sample values; display confidence and require confirmation of uncertain mappings.
5. **Dashboard experiments:** fork a layout or mapping while keeping a common pinned dataset, compare alternatives, and promote one without changing the source recipe.
6. **Data-quality dashboard:** apply the same exploratory tools to quality flags and failed transformations, linking an anomaly back to its source and recipe step.


AI can later propose mappings or explain a recipe, with explicit review and no autonomous execution or silent transfer of data. It is not required for the core product. Embedding exploration and network views are later experiments; the Portic report does not establish a delivered network view.


## 6. Technical architecture


Recommended continuation of the existing stack: Flask backend with a modular API; pandas/openpyxl for initial imports; SQLite metadata and project file storage for the first single-server edition; a durable job table with a separate worker process for API/import tasks. PostgreSQL/object storage are growth paths, not mandatory first-release infrastructure.


Use TypeScript modules and a locked frontend build for the studio, with Keshif isolated behind an adapter. Keep server templates for the shell if useful. Reuse Tabulator initially for the field editor and record table rather than introducing DevExtreme solely because Portic uses it. Client framework choice is secondary to the adapter and state contracts.


Objects: Project, SourceDefinition, ImportRun, DatasetVersion, FieldDefinition, RecipeVersion, DashboardVersion, AnalyticalSnapshot, Cohort, PublicationRelease. Dataset versions are immutable; derived outputs reference parents. Jobs have explicit queued/running/cancelled/failed/succeeded states and structured diagnostics.


Execution model: backend normalizes and validates; the client receives one typed record projection for the active version; Keshif owns interactive selection in that client; the adapter emits normalized selection/state events to other panels. Browser and server transformations share a versioned operator contract; browser previews are validated by the authoritative server operation.


Keshif remains an in-browser engine. Server-side ETL does not make a million-row Keshif dashboard interactive. Profile record count, width, cardinality, and rendering cost. Offer an explicit filtered extract or aggregation when limits are reached; label changes of grain and sampling. Do not silently discard data.


Practical controls intrinsic to this app: restrict API requests against internal/metadata destinations and recheck redirects; store secrets server-side; authorize project access; confine uploaded filenames to managed storage; limit upload/job sizes; escape record content; and protect session-backed write actions. These prevent the proposed generic URL/import features from granting unintended server access.


## 7. Custom Keshif distribution strategy


### Distribution and maintenance


Select an exact baseline revision and inventory all runtime assets. Prefer upstream TypeScript source changes when it can be matched to the deployed distribution and rebuilt faithfully. If the vendored readable module is the practical baseline, retain it as the canonical readable patch target and regenerate minified JS plus a matching source map. Never hand-edit only the minified artifact.


Keep one custom distribution, an explicit patch ledger with rationale and tests, retained notices, and a build manifest with baseline revision and checksums. Portic's tested fixes are reusable candidates, not proof of binary compatibility. Compare its patches against this baseline before importing each one. Build reproducibility and a browser smoke suite gate every distribution update.


### Prioritized changes


| Priority | Change | Layer | Acceptance evidence |
|---|---|---|---|
| Required | Preserve numeric zero/boolean false in type detection | Keshif core + import normalization | Zero-only/false-only columns retain values and usable filters |
| Required | Missing geometry, valid empty bounds, complete cluster membership | Keshif core | No-coordinate dataset renders an empty map; cluster above 1,000 members selects every member |
| Required | Optional external fonts cannot block initialization | Keshif core / local assets | Dashboard and resize work with font requests blocked |
| Required | Hidden-container guards, reentrancy protection, grouped width/height refresh | Keshif core | Repeated tab/panel/view changes retain finite geometry and selected IDs |
| Required | Correct scatter rescaling and map-specific encodings | Keshif core | Axes and point positions match resized dimensions; switching views does not inherit incompatible measures |
| Required | Native navigation for links in record cards | Keshif core + safe template adapter | Link click opens its intended target once without also opening record details |
| Early | Configurable central-view height, optional scatter labels, lazy comparison glyphs | Keshif core | Comparisons remain correct with fewer initial DOM nodes |
| Early | Container ResizeObserver, panel-aware layout, accessible horizontal region | Studio integration | Hidden/reopened dashboard and narrow-screen keyboard use work |
| Early | Exact-ID selection events and normalized state serialization | Adapter; small core hooks if needed | Table, saved state, charts, and export contain identical intended IDs |
| Early | Explicit lifecycle contract: ready, selection change, view change, resize, destroy | Adapter first; core only for missing hooks | Mount/unmount repeatedly without stale handlers or duplicate callbacks |
| Later spike | Canvas scatter rendering with SVG axes and accessible record table | Optional core renderer | Benchmarked gain with exact filtering, hit testing and comparison parity |


Proposed event/serialization contracts are new studio API requirements, not a claim that these exact public APIs already exist. Audit current hooks before adding them. Native Keshif comparisons and panel collapsing remain native features.


Keep source connectors, ETL, project persistence, table integration, chart recommendations, coverage explanations, map-provider selection, and publication out of the Keshif rendering core. Make expensive-view warnings nonblocking where appropriate, but do not globally suppress warnings before measuring practical limits.


## 8. Delivery plan and approval boundary


No implementation starts until the user validates this proposal. Recommended scope is incremental; later phases are not implied authorization to build everything at once.


### Phase 0 — Baseline and contracts


Pin and reproduce the selected Keshif distribution; resolve asset inventory and license metadata discrepancy; audit supported public hooks; define project/recipe/field/state schemas; establish fixtures and baseline performance. Deliver a technical decision record and a small validated chart harness. Gate: source-to-bundle build and selection correctness are demonstrated before feature development relies on them.


### Phase 1 — Useful file-based studio


CSV/TSV/XLSX/JSON import, full validation, stable IDs, editable field dictionary, basic preparation recipes, dashboard/card authoring, synchronized table, save/reopen, private projects, and portable manifest export/import. Include required Keshif reliability patches. Deliver example projects for publications, a generic geographic dataset, and a nonbibliographic tabular dataset. Gate: a fresh user can import, correct, explore, save, reopen, and export the same selected records.


### Phase 2 — Repeatable acquisition and analysis


Generic paginated JSON API connector and OpenAlex preset; import jobs with progress/cancellation/checkpoints; API-to-field mapping; refresh rehearsal; semantic snapshots and pinned cohorts; coverage lens; expanded preparation and joins with grain checks. Gate: controlled refresh changes the version without silently breaking existing snapshots or dashboards.


### Phase 3 — Publication and reusable domain labs


Reviewed publication datasets, read-only releases, French/English polish, reusable Publications/Laboratory templates, dashboard experiments, and quality dashboards. Gate: a published release contains only approved data and is unchanged when its editable project advances.


### Phase 4 — Evidence-driven extensions


Benchmark-led Canvas scatter spike, advanced timeseries tooling, optional embedding workflow, and investigation of linked graph views. Prioritize only after real data and usage identify a need. Do not make these a prerequisite for a useful first release.


## 9. Acceptance and validation matrix


| Area | Required scenario |
|---|---|
| Types and identity | Preserve `0012`, 0, false, null, empty strings, Unicode names, invalid numbers and ambiguous dates; duplicate IDs produce actionable feedback |
| Imports | CSV quoting/newlines, decimal commas, heterogeneous JSON keys, nested arrays, XLSX sheet choice, malformed input, explicit empty input |
| Recipes | Save/replay produces equivalent typed records; undo restores prior output; bad mappings show affected records; row explosion is explicit |
| API jobs | Page and cursor fixtures, rate-limit/backoff, authentication failure, partial import, cancellation, resume constraints, record limits, schema drift |
| Selection | Identical IDs across list/map/scatter/table/export; multivalue membership; missing values; zero-result filters; table predicates survive view changes |
| Geometry | Zero coordinates, no geometry, invalid geometry, role switching, empty spatial result, clusters above 1,000 members, overlapping points |
| Lifecycle | Six consecutive view changes, hidden dashboard, container resize, collapsed panels, reopen, and destruction without accumulated callbacks |
| Persistence | Save/reopen and export/reimport preserve recipes, labels, date semantics, view state, and pinned cohort membership |
| Publication | Private data excluded from browser payloads and exports; published release stays tied to its approved version |
| Accessibility | Keyboard operation, visible focus, labeled regions, contrast, usable table alternative, narrow screens at 390/768px |
| Performance | Benchmark 5k/30k/100k records with variable width/cardinality; record import, first render, filter latency, view switching, memory, and DOM size |


Provisional performance target: common facet actions under 500ms at p95 on a specified reference machine for a 30k-record representative dataset. This is a target to validate during Phase 0, not a promise inferred from Portic. Set supported dataset limits from measurements; a slow or failed 100k stress case is not concealed by sampling.


Use unit tests for conversion/state logic, integration tests for imports/jobs/publication, and real browser tests for interaction and Keshif lifecycle. External API/tile smoke checks are separate from deterministic fixtures. The uploaded report's timings are informative baseline context, not new-app benchmarks.


## 10. Proposed decisions for validation


- Approve the product direction: a project-based studio with a quick upload path and deeper preparation/authoring workspaces.
- Approve Flask continuation, a TypeScript frontend adapter, and a maintained custom Keshif distribution with narrowly scoped patches.
- Approve Phase 0 followed by the file-based Phase 1 as the first implementation scope; keep APIs and refresh workflows explicitly planned in Phase 2.
- Proposed defaults: self-hosted small-team deployment; French/English UI; no mandatory AI service; structured tabular data first.


If the first release must lead with API harvesting rather than files, swap the Phase 2 connector work into Phase 1 and defer secondary authoring features. This is the principal scope tradeoff for validation.
